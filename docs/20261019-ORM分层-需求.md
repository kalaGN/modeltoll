# SQLAlchemy ORM 分层需求

日期：2026-10-19。状态：用户“实施吧”确认详细设计，按切片实施中。
用户要求“做分层”，并明确选择“引入 SQLAlchemy ORM，同时建立表 Model 和数据访问层”。

## 事实与目标

当前后端使用 PyMySQL，未安装 SQLAlchemy；13 张表的 DDL 在 backend/migrations，
12 个业务服务文件直接包含持久化语句，Service 同时负责业务与查询细节。
最新代码提交为 905e2d9，工作区核查为干净；默认回归已有 224 项（上一轮 220 通过、4 跳过）。

目标是 API → Service → Repository → ORM/MySQL，现有每张表建立明确映射类。
Model 不是 Pydantic schema；Repository 不按表各自提交事务，Service 保留跨表业务原子性。

## 范围

- 引入同步 SQLAlchemy 与现有 PyMySQL 驱动，复用数据库配置，新增 models/repositories。
- 覆盖账号、Key、品牌/连接配置、管理审计、统计、计费、调用回执/恢复/幂等及请求限流。
- Service 不再编写持久化 SQL 或 ORM 查询；Repository 负责查询、更新、行锁和结果投影。
- 接口、CLI、客服规则、价格、数据库结构、模型生命周期、锁及单 worker 限制不变。
- migrations SQL 仍为 DDL 唯一来源，不因增加 Model 自动建表、改表或引入 Alembic。

## 验收

1. 13 张表各有映射 Model；列精度、空值、字符排序规则、复合主外键与唯一约束与迁移一致。
2. Service 仅编排业务、权限和事务；Repository 不自行 commit/rollback，不反向导入 Service/API。
3. 所有公开 HTTP/CLI 字段、状态码、Cookie 与响应头不变；完整 OpenAPI 与基线一致。
4. 正常结算与显式恢复共用一套结算；费用、终态、审计、去重等原子边界不变。
5. 单元、契约、MySQL 方言编译与隔离 MySQL 行为测试分别提供证据，不用 SQLite 证明 MySQL 锁正确。
6. 无 ORM 模型/Session 凭据序列化泄漏、默认级联硬删除、N+1 或跨请求共享 Session。
7. 分切片迁移，阶段性混用必须明确；全部切换后才声明完成，不把 Model 空壳称为完成分层。

## 非目标与授权边界

不改 API 响应体系、不引入异步数据库栈、不重构前端、不新增业务功能。
不改变启动迁移策略，不自动提交/推送/重启/部署，不迁移或删除真实业务数据。
隔离数据库测试另使用显式 opt-in 配置，不能默认写入本机 laya_platform。
详细设计已确认，可以安装依赖并按计划实施；不因此扩大真实数据和服务操作权限。
