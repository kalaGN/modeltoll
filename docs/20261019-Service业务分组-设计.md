# Service 业务分组设计

依据：[需求](20261019-Service业务分组-需求.md)，用户已确认方案。

| 目录 | 模块 |
| --- | --- |
| access | accounts、api_keys、admin_management、bootstrap |
| inference | lifecycle（原 inference）、recovery（原 inference_recovery）、model_runtime、customer_service、gateway、request_limits、idempotency |
| metering | billing、statistics |
| platform | branding、admin_overview |

各包 __init__.py 仅含说明，不聚合导出或初始化对象；调用方显式导入业务域内模块。
这是面向业务域分组的分层架构，不宣称完整 DDD。目录不是已正式确认的限界上下文，
ORM Model 仍是表映射，不代表聚合根；本轮不新增值对象、领域事件或领域层。
原 inference/recovery 模块在调用方可使用本地别名保持业务代码不变，不保留旧路径文件。
core/time.utc_now 保留原 naive UTC 和类型语义，调用方直接从 core 导入。
不移动 Repository/Model，也不在各业务域下再建空壳层。领域间允许显式依赖，
仍保持 Service 不导入 HTTP、Repository 不反向导入 Service 的边界。

以受控脚本生成 apply_patch 完成机械迁移，覆盖 Python 源码及字符串内脚本。
先保存 OpenAPI 和默认测试基线，再迁移、补结构/时间测试、回归、同步长期文档。
不删除既有测试断言；仅导入/patch/源码定位路径允许更新。

无数据库或依赖变更，不运行迁移。回滚恢复本次代码即可；运行服务保持旧进程直至用户要求重启。
