# 已撤销 API Key 删除设计

状态：用户确认后已实施。

## 方案

1. 在 backend/migrations 新增 0004_api_key_deletion.sql 与对应回滚，添加 nullable deleted_at DATETIME(3)。通过现有迁移加载机制执行，兼容已存在的数据库；不改旧迁移的既有语义。
2. api_keys.list_for_user 排除 deleted_at 非空记录。公共返回字段不变，状态仍为 active/revoked。
3. 新增 DELETE /v1/api-keys/{key_id}，成功 200 `{ "code": "ok" }`；会话归属、CSRF、UUID 校验与现有路由一致。
4. 服务函数以 user_id 与 key_id 约束 UPDATE，仅 revoked_at 非空且 deleted_at 为空时设置时间；未更新时区分 404、可用 Key 409 与已删除幂等成功。不依赖客户端状态，不用先 SELECT 再无条件 UPDATE。
5. 对已删除 Key 的管理撤销请求返回 404；鉴权保持已撤销拒绝，历史明细 JOIN 保持不变。
6. app.js 在 revoked 行增加删除按钮；新增删除确认弹窗，复用现有焦点与错误反馈。

## 兼容与回滚

仅新增接口与字段；旧调用路径、公共 JSON 字段与统计查询不变。回滚时先撤回前端和接口，再删除 deleted_at 字段；隐藏的已撤销 Key 将重新出现在列表，但不会恢复调用能力。回滚不自动执行。
删除后进行中的推理与记账仍有原始 Key 行可关联，不改变推理锁或结算事务。

## 验证方式

标准库 unittest 验证本人/他人、有效/撤销/已删除、非法 UUID 与 CSRF；真实 MySQL 集成验证只使用新建的隔离测试数据，不改已有用户密钥。以未改变历史统计及外键引用为重点；浏览器验证成功、取消、错误与刷新持久性。
不新增测试依赖，不用假数据库证明真实外键兼容。
