## 1. 依赖与目录

采用同步 SQLAlchemy 2.1 系列 + mysql+pymysql，已在 requirements-api.txt 增加
`SQLAlchemy>=2.1.5,<2.2`，不增加 asyncmy、databases、Alembic 或通用 DAO 框架。
2026-10-19 官方下载页列出 2.1.5 为当前版本；安装时复核解析版本、传递依赖与 Python 3.12
兼容性；实际安装 2.1.5，uv pip check 通过，仍不是依赖锁定。

```text
backend/app/
  api/                  # HTTP/认证/错误和响应；不直接使用数据库 Model
  schemas/              # 既有接口契约，与数据库映射分开
  services/             # 业务规则、跨表编排、事务边界；保持平铺
  repositories/         # 数据查询/写入/行锁与纯结果投影
  models/               # 13 张表的映射，每表一个模块 + base.py
  db/engine.py          # 惰性 Engine 与 Session 工厂
  db/session.py         # 短只读范围、业务事务上下文
  db/connection.py      # 仅迁移使用的原生连接（迁移期允许旧服务临时使用）
  db/migrations.py      # 原 SQL 迁移执行，不调用 metadata.create_all
  core/                 # 既有配置、安全、纯函数
  integrations/         # 既有模型/上游适配
```

Repository 按操作域分为 accounts、api_keys、billing、calls、administration、settings、statistics、
request_limits 八个模块。共享表并不要求共享提交：例如 administration 可查询 users/api_keys/audit，
而账号与 Key 自身接口各用自己的查询。没有通用 BaseRepository、每表 CRUD 空壳或自动 DTO 大包。

## 2. Model 边界

- 使用 DeclarativeBase、Mapped、mapped_column；映射是 DDL 的应用表达，不是第二个迁移来源。
- DATETIME(3)、DECIMAL(20,6)、UNSIGNED、MEDIUMBLOB、ascii_bin 与邮箱大小写敏感 collation
  按 SQL 保留；0004/0005 追加的 deleted_at/is_admin 也必须映射。
- 回执 truncated 保持 int(0/1)/None，避免 Boolean 反序列化破坏严格整数验证。
- 复合 PK/FK/唯一约束显式定义，尤其 api_keys(id,user_id)、调用归属与同用户去重。
- 时间写入显式使用数据库 UTC_TIMESTAMP(3)，不替换为本机时钟或隐式 onupdate。
- 不加自动 delete cascade；初期不铺设未使用的 relationship，也不启用懒加载去序列化。
- Model 不包含业务政策、HTTP 字段或 commit 方法，不使用模型 __dict__ 输出响应。

## 3. Session 和结果边界

- Engine 惰性创建，import app.main 不连接数据库、不加载模型。
- 使用 NullPool 维持当前按操作连接/关闭行为，本轮不顺带做连接池性能优化；连接超时仍 5 秒。
  URL 用 URL.create 从配置构造，echo=False、hide_parameters=True，不打印口令/参数。
- Session 每个操作/线程独立；不把同一 Session 放入 app.state 或依赖后传到多个线程。
- Service 使用短事务上下文，Repository 接收现成 Session，不自行开启第二条业务连接或提交。
- autoflush=False，关键写操作显式执行/flush，保持父 Key、调用、去重等锁与插入顺序；
  注意 commit 仍会 flush，不能以关闭 autoflush 代替异常处理。
- Session 默认过期行为保留；Repository 在有效 Session 内投影为普通字典/既有 dataclass，
  业务层和 HTTP 不持有脱离 Session 后懒加载的 ORM 实体。既有 User/Principal/PricingRule DTO 可保留。
- 锁定检查使用新的 select(...).with_for_update()，必要时 populate_existing，
  不让 identity map 的旧角色/状态替代数据库内二次校验。

## 4. 跨表与特殊事务

1. 账号：密码校验保持写事务外；发 Session 前锁定复核用户状态，停用账号不再拿到新会话。
2. 管理：actor/target 按原 UUID 顺序锁定，再锁 Key；状态或撤销与审计同事务，重复操作不添审计。
3. begin：先锁父 Key，再写 accepted 与同用户去重记录；不靠 Session 自动排序猜测写入次序。
4. 成功回执：业务结果先可 JSON 编码，再以独立短事务保存可信计量事实；随后终态/费用同一短事务。
   不能把回执与结算合为一个事务，否则记账失败时失去恢复依据。
5. 结算/恢复：两条路径共享同一个 Service 事务算法，调用行/费用/原价格/回执检查用同一 Session。
   不因按表建立 Repository 而各表 commit；缺少回执/事实矛盾不推算收费。
6. 去重：捕获 sqlalchemy.exc.IntegrityError 后在事务退出、完成 rollback 后再用新的只读 Session
   查赢家；检查原驱动错误码，不能把所有完整性失败都当重复 Key。
7. RPM：旧窗口清理仍独立提交并释放范围锁；同一计数事务获取数据库时间、占位、锁定和递增，
   跨分钟重试范围仍只有既有窗口逻辑，不增加推理重试。
8. Bootstrap：GET_LOCK、业务事务、RELEASE_LOCK 始终使用一条外部持有的物理连接。
   获取锁后须正确结束 SQLAlchemy SELECT 自动开始的事务，再开始写事务；连接级命名锁不因此释放。
   Session 绑定该连接，提交/回滚不能提前归还连接；释放失败仍保留现有保守失败语义。
9. 不跨等待模型锁、推理、HTTP 上游或密码哈希持有业务 Session/事务。

MySQL UPDATE rowcount：SQLAlchemy 使用 matched rows，原 PyMySQL 默认更接近 changed rows。
必须逐项验证 Key 撤销/删除和 mark_running 三处判断；通过条件 UPDATE 和锁定后状态检查保留
幂等/冲突语义，不能机械照抄 rowcount 判断而不验证。

## 5. Repository 示例与 SQL 例外

以下仅示例，不是已实现代码：

```python
def lock_user(db: Session, user_id: str) -> User | None:
    return db.scalar(
        select(User).where(User.id == user_id).with_for_update()
        .execution_options(populate_existing=True)
    )
```

普通读写使用映射实体的 select/update/insert；复杂统计可用 SQLAlchemy Core 聚合/显式 join。
MySQL upsert、INSERT IGNORE、命名锁等优先使用方言构造或函数表达式；如果仍需参数化 text SQL，
仅允许留在 Repository 或迁移器并记录理由，不能把原 SQL 简单搬进一个万能 execute 包装器冒充 ORM。
Repository 不导入 Service；业务判定由 Service 决定，返回字典/DTO前的投影不触发关系查询。

## 6. 分批迁移和验收

先建基础与所有 Model，但尚未切换的模块必须明确标识；按配置/品牌 → 账号/Key/管理 →
统计 → 计费/调用/回执/恢复/去重 → 限流/Bootstrap 的顺序切换，每批有可运行回归。
最终 Service 禁止 SQL 和 ORM 查询；迁移器原生连接保留，业务旧游标入口全部退出后移除，
不长期保留运行时开关或双写两套后端。

测试分四类：
- Unit：业务政策、Session 生命周期、回滚和异常语义，原业务断言保留。
- Contract：现有 224 项中对应 HTTP/CLI 行为与新增独立边界；完整 OpenAPI 比较。
- SQL/Model：MySQL 方言编译、13表列/约束映射、UTC/Decimal/复合键/条件 UPDATE/锁语句。
- 独立 MySQL：按原 SQL 创建空测试库后反射对照 Model；真实并发去重、限流、管理员初始化、
  撤销/停用竞态、恢复幂等和费用/审计回滚。SQLite 与 mocked Session 不作为锁语义证据。

不能只重写旧 FakeCursor 测试为 Repository Mock 就声称原数据库行为未变。
旧 HTTP 桩可以沿用，SQL Fake 必须由方言编译和隔离 MySQL 证据补齐。
